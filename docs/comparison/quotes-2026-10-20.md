## E workflow

1. Press `E`. Neovim opens a vertical diff immediately: immutable original on the
   left, editable plan on the right. Both files and their directory are private.
2. Edit `updates[].row`; add new objects to `insert`. Removing an update entry
   skips that row. Deletions must be explicitly listed in `delete`. Do not edit
   original identity/snapshot objects.
3. Review changes in Neovim (`]c` / `[c` navigate differences; `zR` opens folds). Use `:wqa` to return
   or `:cq` to cancel. An unchanged plan dispatches no mutations.
4. The browser displays operation counts and asks for confirmation. Confirmed bulk
   changes run atomically. Explicit deletions require the `DELETE` acknowledgement.

There is no large built-in bulk JSON editor or full-row TUI diff in this flow.
Single-row editors retain their existing behavior. `DBCLI_BULK_EDITOR` accepts a
quoted Neovim command prefix, without a shell. Go/Rust honor the user configuration
while disabling swap/backups/persistent undo; Python currently defaults to a clean
Neovim profile. Timings use clean Neovim for every language.

The existing 100,000-row bulk limit remains. Go also bounds the editor payload to
128 MiB. This is a bounded in-memory editor, not streaming editing of arbitrary
table sizes. Go files duplicate primary-key tokens alongside editable rows; Rust
and Python also duplicate full original snapshots. Immutable full snapshots remain
in application memory for conflict checks in every updated implementation.

### Correctness, editor checks and limitations

Backend validation: 10/10 candidates; 80 validated workloads. Timed outputs are checked too. Oracle stable after the run: **True**.

UI timing readiness: **108/108**. Clean lifecycle checks: **108/108**. Updated in-Neovim unsaved diff checks: **54/54**. See JSON for individual statuses; readiness timings and cleanup outcomes are recorded separately.

Application benchmark generated-write attempts observed by the packet guard: **0**. Every actual Neovim session exits `:cq 23`; no application-data confirmation or write is performed.

The original in-run tree sampler could miss child processes spawned from Go runtime threads. Its raw tree fields are retained for audit but are not used in the tables. The corrected sidecar enumerates every task’s children. Direct-child Neovim rusage fields only cover the launcher/UI process and exclude the forked backend, so they are not used as whole-editor CPU/peak-memory metrics.

The four legacy Go renderers can scroll the initial table heading offscreen for this wide table. The harness detects their completed raw header in memory and records visibility separately. This existing rendering issue is not a database latency failure; use the modern Bubble Tea UI for this workload.

The separate and integrated Go copies currently use different Go toolchains (see table). These are comparisons of the pinned available builds, not isolated compiler/language experiments. Rust integrated/separate copies are not independent implementations.

Mutating feature verification used only disposable fixtures: Go 48 real-Neovim SQLite/PostgreSQL scenarios; Rust 32 real-Neovim scenarios plus legacy SQLite PTYs; Python 49 frontend tests, eight real PTY scenarios, and 51 PostgreSQL checks. These cover unchanged/cancel, edit/confirmation, sparse changes, rollback, typed values, private-file cleanup and terminal restoration. Reference offline suite: 35 passed, two optional live-integration skips. Launcher suite: 45 passed. Harness regressions are reported separately.

## Method and limits

- Target: the explicitly authorized PostgreSQL 16 container `602a0e2d7656…`,
  `public.quotes`. RLS is enabled; reads retain the original owner visibility.
- Read results are compared with the reference using column types, preserving
  SQL NULL versus JSON null, UUIDs, numeric values and timestamps. No row values,
  database credentials or application screenshots are retained in evidence.
- Insert/update/delete correctness is checked on disposable fixtures; application-table mutation latency is not measured. MySQL benchmarks are not part of this phase.
- Backend workloads cover first/next pages, ascending/descending order, filtering,
  count, schema, identical supplied raw SQL, and full bounded bulk fetch. Native
  page endpoints do not automatically count rows; the Python UI does. The raw SQL
  case provides the query control. SQL wrappers and connection setup can still vary.
- Repeated warm samples reuse worker processes and randomize candidate/workload
  order. Connections are normally short-lived per operation. Fresh-process startup
  repeats process creation plus one query nine times. Database/OS caches are not cleared; this is not a cold-server
  experiment. The application container is never restarted.
- UI runs use real POSIX PTYs and Neovim 0.12.5, with a clean configuration. Baseline
  modern UIs require `E` then `Ctrl+G`; their timings include both keys. Updated
  variants use `E` directly. Every live editor cancels with `:cq 23`; there is no
  application-database write or confirmation.
- A benchmark-only local PostgreSQL packet guard rejects generated CRUD/DDL before
  forwarding. The same proxy is used for all UI variants. Connection setup for
  writable interfaces remains permitted. This controlled-workload guard is not an
  untrusted-SQL sandbox. Direct backend timings do not use the proxy.
- UI memory is summed across UI, worker and Neovim at editor readiness, excluding
  the measurement wrapper. Shared pages can be counted twice. Backend memory/CPU
  only covers the worker; PostgreSQL CPU is excluded. CPU ticks are coarse (10 ms).
- Go build versions differ between some separate and integrated copies; the artifact table records them. Measurements compare these available builds, without claiming to isolate a language or compiler effect.
- This is a shared workstation. Randomized repetition reduces order bias but does
  not eliminate background activity. Build/test jobs finish before final timings.
- Variant names retain their historical ancestry. The updated variants all received further Codex changes and share one frontend per language; this is not a controlled comparison of the original coding agents.
- Integrated Go/Rust ports are explicitly copied, pinned builds of the separate
  ports, rather than independent rewrites. Small timing differences are noise.
